# Research record: CI and delivery (2026-10-29)

This record is never edited; a later round gets a new file. Dan asked for it after the first CI outline felt "raw": he asked what large projects do, what CI architecture holds up as the app grows without wasteful hour-long jobs, and what the whole picture is ([brief](../brief/2026-10-29.md)).

2. [Runners and cost](2026-10-29-delivery/2-runners-cost.md): GitHub's 2026 prices, third-party and self-hosted runners, cross-compiling, signing from Linux, worked cost examples.
3. [The desktop release](2026-10-29-delivery/3-desktop-release.md): Dioxus bundling, Velopack, Windows and macOS signing, how Zed, Warp, Lapce and Tauri apps ship, rollback, enterprise installs.
4. [Supply-chain evidence](2026-10-29-delivery/4-evidence.md): the EU Cyber Resilience Act, SBOMs, provenance, GitHub security features by plan, what enterprise buyers ask for, secrets in CI.
5. [Everything else that ships](2026-10-29-delivery/5-other-delivery.md): the web app and website, the API server, real-dependency tests, packs as releases, the scheduled watcher, the CLI for customers' CI.

**Limits:**

## What the research found

1. **Big Rust apps stay on plain Cargo and GitHub Actions.** Zed, Ruff, uv, Bevy, Tauri and Deno keep CI at about 7–65 minutes with five levers: bigger runners, caching, running only what a change affects, tiers, and hard timeouts. None uses Bazel. Bazel and Buck2 appear only in very large or multi-language codebases (appendix 1).
2. **The hour-long job is prevented by tiers, not by a bigger machine.** Per push: only what the change affects. Scheduled: the full suite and the other operating systems. At release: signing and packaging. The thresholds for each lever are measured CI time: about 5, 10 and 20–30 minutes (appendix 1).
3. **Today's workload costs $0.** The Free org plan includes $12 of compute a month: 2,000 Linux minutes, or 1,200 Windows, or about 193 macOS minutes. Each job rounds up to a whole minute, so fewer, longer jobs are cheaper. macOS dominates any bill. One hung macOS job at the default 6-hour timeout costs about $22, nearly two months' allowance (appendix 2).
4. **Cross-compiling doesn't pay.** Windows from Linux saves cents and `dx bundle` doesn't support it. macOS from Linux is forbidden by Apple's SDK licence. So releases need a Windows runner and a macOS runner (appendices 2 and 3).
5. **The desktop release has a well-trodden shape.** Build natively on each OS. Velopack packages and signs; Dioxus only builds. Upload to staging, test the exact files, then publish the update feed last. Rolling back needs client support that ships from version 1. Updates are hosted on R2, because a private repo's GitHub Releases can't serve the public (appendix 3).
6. **The Free plan can't enforce anything on the server.** It has no branch protection, rulesets, environments, merge queue or private-repo attestations. "Main is always green" works on Free only as a habit: push to a staging branch, and CI fast-forwards main when it passes. GitHub Team ($4/user/month) can enforce it, still without pull requests (appendices 1, 4 and 5).
7. **The EU's Cyber Resilience Act already matters for anything placed on the EU market.** Its reporting duty has applied since 2026-09-11, including to free betas unless they're labelled as test software. The main obligations apply from 2027-12-11: an SBOM in the technical documentation, security updates "without delay", a disclosure policy, a declared support period and 10-year retention. A compromised build pipeline or signing key is a reportable incident (appendix 4).
8. **Everything else has cheap, standard homes.**
   - **Web app and website:** Cloudflare Workers static assets, uploaded as a version, smoke-tested, then deployed.
   - **API:** one binary in an image, migrations run by the pipeline before traffic moves, deployed with Kamal or systemd.
   - **Packs:** a contents hash, tests for changed packs only, minisign signatures.
   - **Watcher:** scheduled twice daily, with an outside missed-run alarm.
   - **CLI:** released into a public repo with dist, plus an Action and a container image.

   Source: appendix 5.

## Proposals for Dan (not decided)

These go to Dan as options; nothing here is decided.

1. **The architecture: a delivery system in tiers.** It would be one decision, with each tier switched on by a phase or a measured threshold, not built ahead of need:
   - **Gate:** every push. One Linux job, with a time limit and a time budget. It adds affected-only tests and a shared cache on R2 only when it passes about 10 minutes.
   - **Scheduled:** daily. A security-advisory check; later the full suite and unsigned Windows and macOS builds, skipped when main hasn't changed.
   - **Release:** on a version tag, ending in a manual promote. Native builds per OS, signing, Velopack packages, the CLI, an evidence bundle (SBOM, checksums, versions) kept outside GitHub, and the update feed published last.
   - **Deploy:** phase 3, for the web app, website and API.
   - **Data:** packs and the watcher, from phases 1 and 4.
2. **How main stays green:**
   - push to main and fix forward (today)
   - a staging branch that CI fast-forwards
   - the staging branch plus GitHub Team to enforce it
3. **How spending is capped:**
   - no payment method, so CI stops at $12
   - a payment method with a budget that stops usage
4. **Small changes now:**
   - a time limit on every job
   - a per-test time limit
   - the daily advisory check
   - Dependabot alerts (alerts only, since its update pull requests conflict with the no-PR rule)
5. **An exception to the two-week pin rule for security fixes.** The CRA asks for them "without delay". This would change a rule in CLAUDE.md, so it needs Dan's words.
6. **Decisions that can wait for their phase:**
   - the legal entity and country for code signing (Azure Artifact Signing takes individuals only in the US and Canada)
   - Intel Mac support
   - when to ship an MSI
   - public repos for the CLI and Action
   - Kamal or systemd
   - GitHub Team or Enterprise
   - how provenance is signed
   - where the evidence archive lives
   - the support period
   - an EU beta
   - legal review of the CRA classification
